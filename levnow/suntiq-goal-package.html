The acceptance contract — how a scenario proves itself

The done-condition is deliberately falsifiable: a labeled scenario pack enters through the production-equivalent ingest (never a parallel seam), its synthetic provenance stays visible through storage and every evidence output, and a per-screen oracle defines the expected state for every operator surface — including legitimately empty "collecting data" states. The three receipts correlate by run id and ingest ids; a run missing any link proves nothing. Crucially the oracle carries negative assertions: an insurance report that renders the sim trip as real evidence is a contract FAIL.

DECISION BRIEFS

The two new decisions, in full

Both are drafts awaiting your acceptance. Both were adversarially reviewed and repaired across four cycles.

📼

Raw telemetry capture first (ADR-007)

Problem: the data-placement decision left a tension open — start the GCP archive now, or at a ~50-boat trigger? Meanwhile the ingest already writes every connection's raw bytes to captures/*.bin… on a 1 GB droplet disk. Twenty boxes are inbound.

Decision: split the tension by tier. The RAW tier archives NOW: rotate the existing capture files hourly → gzip → gs://suntiq-telemetry-raw/raw/boat=<code>/date=<d>/, written by a create-only service account (no delete permission), lifecycle to cold storage at 30 days. Parquet and BigQuery stay out of scope until the decoded-tier trigger.

Why it matters: raw CAN is the only loss-proof representation. Decoded rows inherit every decoder bug; raw can always be re-decoded when a new PGN or a decoder fix lands. This tiny pipeline is also deliberately the first SuntiQ GCP resource — project, billing, and IAM bootstrap happen on a workload where nothing can go badly wrong.

Consequence: ground truth survives VM loss from box #1 onward, and every later data decision becomes reversible.

📜

Append-only telemetry history (ADR-008)

Problem: telemetry lands via an upsert; history rows are not structurally immutable; retention pruning predates any archive guarantee. ML training, debriefs, benchmarks, insurance evidence, and the simulator's honesty path all assume history that cannot be silently rewritten.

Decision — a two-tier contract: the LIVE tier is one mutable snapshot row per boat (a cache — upserts are fine). The HISTORY tier is append-only: every accepted report inserts an immutable event (boat, time, fields, source, ingest id for idempotent replay). No mutation outside the archiver may update or delete a history row.

Provenance is server-owned, classified by what each client can actually prove — the box-from-China section below explains the dtu case. A report whose origin cannot be resolved is rejected or quarantined as unverified, never defaulted to real.

Migration honesty: writers are additive, but readers are NOT assumed unchanged — the cutover requires a dataset authority contract: the legacy/new write boundary and completeness watermark get recorded; each consumer declares its permitted sources (real-only, sim-permitted, mixed); evidence-grade readers fail closed below the watermark; and every history reader gets a semantic audit so a late backfill cannot silently change previously issued aggregates. Your launch-with-watermark ruling plugs directly into this contract.

RECEIPT MECHANICS

Two receipt types, one hard rule

Why a raw backup can never authorize deleting decoded history — the invariant that makes archive-before-prune mechanical instead of aspirational.

    GCS["GCS raw bucket<br/>create-only service account"]
    RR["RAW receipt<br/>object path + byte checksum<br/>+ capture window + boat"]
    CAP --> GZ --> GCS --> RR
  end
  subgraph DECPATH["DECODED tier — ADR-008"]

    ARC["archiver<br/>decoded archive object"]
    DR["DECODED receipt<br/>archive object + row count<br/>+ ingestId-range match"]

    HIST --> ARC --> DR --> PRUNE
  end
  RR -. "proves raw durability ONLY<br/>can NEVER authorize row deletion" .-x PRUNE

RAW and DECODED receipt flows

RAW receipt — what it proves

One receipt per shipped capture object: GCS object path, byte checksum, capture time window, boat. It proves exactly one thing — the raw byte stream for that window is durably stored off the VM.

It says nothing about decoded rows, because the mapping raw→rows is not one-to-one: the decoder drops out-of-range values, reassembles multi-frame messages, and one frame can fan out into several fields. A raw file can be perfectly archived while the decoded rows derived from it are wrong, missing, or duplicated.

DECODED receipt — what it authorizes

Produced by the archiver when it exports history rows: archive object, row count, and the ingest-id range, all matched back against the history tier before the receipt is recorded.

Only this receipt authorizes retention pruning, and only for the exact rows it names. The deletion code path takes a receipt reference, not a date range — which means "archive before prune" stops being a convention someone remembers and becomes a precondition the code cannot skip.

The rule that survived adversarial review

Each deletion class must name its authorizing receipt type. The reviewer's original finding was that the first draft conflated the two receipts — under which a raw backup would have quietly licensed deleting decoded history that was never actually archived. The split is now explicit in both decision documents.

DTU DEEP DIVE

Is port-per-box really the only option? No.

A vendor-doc inspection this session found two documented in-stream identity mechanisms in the appliance's own protocol suite. Here is the evidence and what it changes.

The blocker: server-fleet.js stamps every TCP connection with one BOAT_CODE environment variable (dtu-ingest/server-fleet.js:46,69). Twenty boxes hitting port 5001 would all write as the same vessel. The appliance is fixed-firmware — you edit a config.ini over USB, you cannot run code on it — so identity must come from network arrangement or from what the firmware already emits.

The design committed to port-per-box as the deployable baseline (twenty listener ports, one per vessel, configured during the hand USB setup each box needs anyway). That decision stands. What changed today is the quality of the alternative: the "stream identity" option went from speculative to documented.

OptionHow it worksVerdict after evidence
A · Port-per-box20 systemd instances, each PORT + BOAT_CODE; each box's config.ini points at its own port.COMMITTED BASELINE. Zero code, zero firmware risk. Ugly at 20, unmanageable at 100 — an honest bridge.
B · Source IP mappingMap the connection's remote address to a boat.REJECTED. Cellular carrier-grade NAT makes source addresses shared and unstable.
C · In-stream identity (Format 5)Set [4G] Format = 5 in config.ini: the firmware prepends the device serial's last four digits to EVERY frame. (E) · Cloud protocol (Format 80)Full framed protocol with custom 16-char serial, register/auth/login/heartbeat frames.DO NOT BUILD ON IT. The protocol doc is stamped unpublished and those frame types carry no completion mark — assume absent from shipped firmware.
📡

The Format 5 evidence

The vendor's frame-format definition (dtu-ingest/vendor-docs/4G记录仪消息帧格式定义20250416.pdf) specifies five wire formats. Format 1 is what we run today. Format 5 is defined as "Format 1 with the last four digits of the SN prepended" — a 4-character string (e.g. "1234") before every frame, worked example included in the doc.

That means identity arrives with the very first telemetry frame, survives reboot and reconnect by construction (it's the hardware serial), and requires no protocol handshake the firmware might not implement. It is selectable today: the factory config.ini exposes [4G] Format with documented values 1–6 and 80; ours currently says 1.

One consequence for our side: the current frame parser would desync on the extra four bytes, so ingest needs a small Format-5 parser variant — roughly a ten-line change, isolated in the framing layer.

🚫

The Format 80 trap (and why we're avoiding it)

The cloud-platform protocol (V1.1, June 2025) looks like everything you'd want: 0x55-framed messages with XOR checksums, a configurable custom serial up to 16 characters (Sn = {1,<boatcode>} — you could literally put the boat code in the device), plus device register, authenticate, login, logout, and heartbeat frame types.

But the document is stamped 未发布 — unpublished — and in its own frame-type table only CAN data report/send and GPS report carry completion marks. Register, authenticate, login, and heartbeat show none. Building our identity scheme on frames the shipped firmware likely doesn't emit would put an unverifiable vendor promise on the critical path — exactly the failure mode the adversarial review kept hammering. It stays on the watch list for a future firmware revision, nothing more.

One genuinely useful find in the same doc: the protocol defines platform→device CAN transmission. Our boxes are configured listen-only (Mode = 1) precisely so nothing can ever transmit onto a customer's NMEA 2000 bus — worth keeping in mind as a standing safety property.

🔬

The spike, now concrete (bench, box #1)

1. Set Format = 5 in config.ini, power from DC, confirm the 4-byte serial prefix appears on the wire. 2. Confirm the prefix survives reboot and cellular reconnect. 3. Inventory all 21 devices' serial last-4 for collisions — four digits across 21 devices are likely distinct within a manufacturing batch, but that must be verified, not assumed. A collision demotes just the colliding pair to port-per-box. 4. Add the Format-5 parser variant to ingest and route by serial→boat map.

The promotion criteria from the design map cleanly: stable across reconnect ✓ (hardware serial) · available before the first telemetry frame ✓ (every frame) · fail-closed on unknown identity ✓ (unknown serial → capture-only quarantine) · operator-configurable ✗ (factory serial — mitigated by the server-side map, same shape as the port map) · unique per device = the one open check.

What ships vs what's next

Port-per-box still ships for the 20-box arrival — it cannot fail and the boxes need hand configuration regardless. But the Format-5 spike is now cheap and well-defined; if it passes, the twenty listeners collapse to one port with in-stream identity, and the ingress lease/quarantine machinery carries over unchanged. The connection→boat mapping module stays isolated either way, so the swap is a config change, not a rewrite.

DISEASE 1

The browser pretends to be the server

Six P0s, one pattern. Every finding below is a screen holding a local copy of a fact the server owns — and letting it diverge.

What "server vs browser" means here. The dashboard has two kinds of state. Server state lives in Convex — locks, memberships, zones, alerts — and is what every OTHER device, the audit trail, and the automation crons see. Browser state is a local convenience copy (a component store, localStorage) used to render quickly. The app's architecture rule, written in its own code comments, is that the browser is a projection: it may cache server facts but never be the authority for them.

The bug pattern is always one of three shapes: (1) optimistic write without rollback — update the local copy, fire the server mutation, and when the server refuses, keep the local copy anyway; (2) fire-and-forget with fake success — apply locally, toast "saved," and route the server rejection to a console nobody reads; (3) local-only authority — the feature was only ever wired to local state, so the server never hears about it at all. All six findings below decompose into these shapes, which is why the fix is a pattern too: await the server, render what it answered, and surface refusal as refusal.

DISP-01 · A refused unlock still unlocks the boat (shape 1)

Where: src/live/cloudService.ts:110-124 and src/screens/DispatchScreen.tsx:303-315, 538-539.

Mechanism: when an operator returns a boat to service, cloudReturnToService calls the server mutation — and in its error handler still applies the local unlock before re-throwing. The screen catches the error and only shows a toast; it never re-locks. The row's button then reads the local store, so it flips to "Check out." The bitter detail: the LOCK direction in the same file does this correctly — refusal keeps the local state locked. Only the unlock direction fails open.

What an operator sees: the server refuses the unlock (say, a role restriction), the operator gets an error toast — and the boat still shows as available on this device. This tablet can now dispatch a vessel every other device correctly shows as locked out of service.

Fix: mirror the lock direction's fail-safe — on rejection, do not touch local state; re-render the still-locked truth. Lands in the parity loop; a sim scenario with a server-locked boat trips it on the first replay.

ORG-01 · The team-management panel is dead for every customer (shape 3, by accident)

Where: src/screens/SettingsScreen.tsx:500 → src/components/OrgPanel.tsx:443 → src/components/MemberManage.tsx:174, 253-254.

Mechanism: a prop threading hole. The settings screen mounts the org panel without an orgId; the org panel internally resolves the active org for its billing display but forwards the raw, still-undefined orgId prop to the member-management component. That component's guard (orgId && orgId !== ALL_ORGS) is therefore permanently false — it renders "Select an organization to manage its members" forever. A second, independent hole: no production caller passes the viewer's own role/user id, so even with the org resolved, the component would default the org OWNER to viewer rank and hide the invite/remove/role controls.

What an operator sees: Settings shows the org's live billing plan correctly, and three lines below it, the entire Team roles & memberships feature claims no org is selected. Unreachable for every customer in production.

Fix: one-line resolution (orgId ?? billingOrgId) — the pattern already applied to the pairing panel ten lines down — plus threading the caller's real role and user id from the org listing query.

GEO-01 · Built-in zone toggles are localStorage theater (shape 3)

Where: src/screens/GeofencesScreen.tsx:657-663, src/live/zonePrefs.ts (pure localStorage), convex/geofence.ts:107.

Mechanism: toggling a built-in zone writes a browser localStorage key — nothing else. Server-side breach evaluation short-circuits to an empty list for any cloud org (if (orgId !== undefined) return [] — line 107), so the four built-in zones are never evaluated for a real club regardless of the toggle. Meanwhile the screen's "in violation now" tile is computed by a client-side library from those same zones — so it lights up red for a breach that generates no alert, no notification, no webhook, nothing.

What an operator sees: they enable a zone, watch a boat cross it, see a red violation badge — and reasonably believe the fleet is protected. With the dashboard closed, nothing is watching at all.

Fix: server-authoritative built-ins — either materialize them as real per-org zone rows at onboarding, or make server breach evaluation consult a per-org enabled map. The toggle writes through Convex; localStorage becomes at most a render cache.

GEO-02 · Custom zones: fake success toasts (shape 2)

Where: src/live/cloudZones.ts:177-276 (warnMirror swallows every rejection into console.warn), src/screens/GeofencesScreen.tsx:706-717, convex/zonesCloud.ts:104 (admin-gated), :51-62 (3–64 vertex bounds).

Mechanism: every zone create/edit/toggle/delete applies to local state synchronously and toasts "Zone added" immediately. The server mutation runs as a detached fire-and-forget whose failure handler only logs to the console. The server, meanwhile, enforces two things the client never checks: admin role, and polygon vertex bounds. So a viewer-role user, or anyone drawing a 70-vertex polygon, gets a full success experience for a zone that was never created.

What an operator sees: a rendered, enabled-looking geofence that exists only on this device. On every other device — and for the server-side enforcement that matters — the zone does not exist. No error ever surfaces.

Fix: await the mutation before toasting; surface rejection as a visible error; add the missing client-side role gate so non-admins can't draw in the first place (the screen currently has zero role checks).

ALRT-01 · Man-overboard has two acknowledgement authorities (shapes 1+3 combined)

Where: src/live/mobStore.ts (header comment: "No backend"), src/components/AlarmCenter.tsx:76-85, 223, 290-351, src/screens/MapScreen.tsx:398-399, 617-619, convex/safetyAlerts.ts:42, src/live/cloudSafety.ts:98.

Mechanism: one MOB event lives in two unsynchronized systems. The persistent emergency banner is driven purely by a client-local store whose only dismiss path is the map screen's "Clear MOB" — a localStorage write with no server call. The same event is also mirrored into the shared alerts table as a critical row, which renders as a normal alert card with its own real server-backed "Ack" button — stacked on the same screen, below the banner.

What an operator sees: clearing the MOB banner leaves the alert row open in the queue and audit trail forever; acknowledging the alert row leaves the emergency banner up. Two contradictory MOB UIs at once, during the highest-stakes workflow the product has.

Fix: one event, one authority. "Clear MOB" routes through the same server acknowledge mutation as the alert row, and the banner derives its presence from that row's acknowledgement state. The local store becomes a pure render cache or is deleted.

ZONES-P0-01 · The Live Map ignores the Geofences screen entirely (shape 3, plus duplication)

Where: src/screens/MapScreen.tsx:6, 521 vs src/screens/GeofencesScreen.tsx:825-826, 905-906.

Mechanism: the primary Live Map passes the raw static built-in zone import — all four zones, hardcoded enabled — straight into the map component, never filtered through the operator's enabled/disabled preferences, and passes no custom-zones prop at all. The Geofences screen's own embedded map does all of this correctly. The logic simply was never shared: two screens, two divergent wirings of the same map component.

What an operator sees: disable a built-in zone, or draw a new custom zone, in Geofences — then switch to the Live Map, the screen that actually sits on the bridge display, and see the old zone set with your custom zone missing. The two screens disagree about what boundaries exist on the water.

Fix: extract the zone-selection logic (enabled built-ins + custom zones) into one shared hook both screens consume. This also erases the duplicated map wiring the spec audit flagged separately.

DISEASE 2

Telemetry has no provenance

Four findings that together mean: the moment synthetic data exists, every evidence surface would present it as real. This is why the provenance rail is plan step 3, before any parity loop.

Disease one is about facts diverging between browser and server. Disease two is deeper: a fact the system never records at all — where a telemetry row came from. There is exactly one source field anywhere in the schema, and it belongs to an unrelated webhook cursor. No table distinguishes a row written by the real boat pipe from one written by an edge box, a backfill script, or a simulator. Today that's moot because no simulator writes to the cloud; the plan makes it existential, because the goal is precisely to pump ten scenarios of synthetic data through the production ingest. Without the discriminator, sim parity would poison every evidence surface as a side effect of testing it.

INS-01 · Insurance reports assert "real evidence" with no way to know (P0)

Where: convex/schema.ts:434, 490, 846 (telemetry, telemetrySamples, rentalScores — no source field anywhere), convex/lib/insuranceReport.ts:91, src/screens/InsuranceScreen.tsx:282.

Mechanism: the insurance screen renders, verbatim: "Every figure is computed deterministically from real rental, maintenance and engine-bus evidence — never AI-generated." Neither the source tables nor the report input type carry any field that could falsify that sentence once synthetic rows exist in the same tables.

Why it blocks parity by definition: the acceptance contract requires synthetic data to be visibly synthetic on every evidence output. This screen structurally cannot comply.

Fix: the source: dtu | edge | sim discriminator from the append-only decision, threaded through the report input, with the screen's claim gated on it — real-only reports keep the sentence; anything else labels or excludes.

INS-02 · Partial evidence renders identically to full evidence (P0)

Where: convex/lib/insuranceReport.ts:129-130, 625, 658, 679, 776-780 versus the screen, which never reads these fields (zero matches for coverage/disposition in InsuranceScreen.tsx).

Mechanism: the report engine is honest — it tracks which of the four weighted risk factors (behavior, incidents, compliance, faults) were actually available, reallocates weights among only those, and exposes coverage and disposition on every report. The screen throws that honesty away: it renders the band and the score and never shows the coverage.

What an underwriter sees: a "Preferred" risk band computed from two of four factors is pixel-identical to one backed by complete evidence. Only the fully-empty case surfaces (as an insufficient-data chip); the partial case is silent.

Fix: render the fields that already exist — an "N of 4 risk factors available" chip on the report card, consistent with the evidence-floor gating the fleet-health surface already does.

INSIGHT-1 · The schema gap feeds every intelligence surface blind (P0)

Where: convex/fleetHealth.ts (~line 952 query), convex/optimizer.ts, convex/ml.ts, convex/telemetryHistory.ts:426 (the ML training row type) — all read telemetry generically with no provenance in the row shape.

Mechanism: the same missing field, seen from the consumers' side. Fleet health's revenue-at-risk queue, the optimizer's utilization report, cross-club network benchmarks, and the ML training pipeline all consume telemetry rows with no way to include or exclude by origin.

Why it matters beyond insurance: ML training on blended sim+real data silently corrupts models; a benchmark comparing a real club against a simulated one is fiction presented as comparison.

Fix: this is why the fix lands WITH the append-only refactor rather than as a UI patch — one discriminator on the history event, propagated to the training row type and every scorer, is one migration instead of five retrofits. The dataset authority contract then has each consumer declare its permitted sources and fail closed otherwise.

SIM-1 · No path exists from any generator to cloud Convex (P0 — a build, not a bug)

Where: boat/demo.ts:9-23, boat/gateway.ts:16, 38 — the only synthetic generators in the repo POST to a local consumer-era boat server on port 8088. Zero Convex imports anywhere under boat/; no simulator directory exists in the fleet dashboard.

Mechanism: the existing demo tooling belongs to the pre-pivot consumer prototype's architecture. The cloud dashboard has never had a synthetic feed; every intelligence surface has only ever been exercised by real ingest or hand-seeded rows. The simulator workstream is at phase zero.

Consequence for the plan: step 3 is a build, not a wire-up — generator, sim-lane service key, manifest/ack receipts, all of it. This is the largest single work item between here and the first oracle run, which is why it owns its own plan step with step 4 explicitly forbidden from starting before it exists.

Fix shape: the generator speaks the same wire contract as production ingest (tracking.reportTelemetry, batch variant for replay bursts) so the sim exercises the real path — never a parallel seam that could pass while production ingest fails.

Scheduled, not blocking

Three more findings that shape the work but don't gate the first slices.

Three screens, three definitions of "underway." The same boat at the same instant can count as underway on the dashboard KPI and not on the dispatch board, because each surface reimplements the predicate with different constants. This promotes into the parity loop because sim scenarios exercising edge speeds and staleness will trip the disagreement immediately — and the oracle can't define one expected state while the app holds three definitions. Fix: one shared isUnderway(boat, now) predicate all three call.

The design-system fork (P0, structural)

The repo's design-system package defines 10+ primitives (Card, Modal, StatTile, Toggle, …); the fleet dashboard imports none of it — its own 532-line src/components/ui.tsx reimplements the same names on a different token substrate (inline styles + CSS-var indirection, by design). It shapes the roadmap but deliberately does not block parity.
