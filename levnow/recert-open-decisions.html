DECISION 1

Callsign Config: Every Permutation Declared, Nothing Derived

Your call was right — derivation was a workaround. Here is what the config-key design looks like concretely.

How it works today. Sources store exactly two placeholders: {{CALLSIGN}} and {{CALLSIGN_SPOKEN}}. At projection time the resolver reads the tail from the scenario's /callsign field (or /flight_plan/registration, falling back to N17XX) — and then computes the spoken form in Python (expand_callsign()). So one of the two forms is already code-derived, and any new form (abbreviated, type-prefixed) would have piled more phraseology rules into code.

Why that's wrong here. The repo's own hoisting law says phraseology vocabulary lives in typed data contracts, never Python rules. And the corpus already proves the rules break: the Canadian scenario's abbreviation is Golf X-ray X-ray X-ray — no N-prefix rule produces that. It even already declares abbreviated_callsign as a config field. The config surface half-exists; the fix is to finish it, not to bypass it with code.

The design you asked about: one required config block holding every spoken permutation a scenario's radio traffic can use. Placeholders map one-to-one onto keys. The projector substitutes only declared keys and fails closed on anything missing — same fail-closed check that exists today.

callsign block (per-scenario, with a corpus-wide N17XX default)
"callsign_config": {
  "registration":       "N17XX",
  "spoken":             "November One Seven X-ray X-ray",
  "abbreviated":        "17XX",
  "abbreviated_spoken": "One Seven X-ray X-ray",
  "short_spoken":       "Seven X-ray X-ray",
  "type_spoken":        "Skyhawk One Seven X-ray X-ray"
}

// placeholder -> key, one to one:
//   {{CALLSIGN}}              -> registration
//   {{CALLSIGN_SPOKEN}}       -> spoken
//   {{CALLSIGN_ABBR}}         -> abbreviated
//   {{CALLSIGN_ABBR_SPOKEN}}  -> abbreviated_spoken
//   {{CALLSIGN_SHORT_SPOKEN}} -> short_spoken
//   {{CALLSIGN_TYPE_SPOKEN}}  -> type_spoken

// Canadian scenario declares its own complete block:
"callsign_config": {
  "registration":       "C-GXXX",
  "spoken":             "Charlie Golf X-ray X-ray X-ray",
  "abbreviated":        "GXXX",
  "abbreviated_spoken": "Golf X-ray X-ray X-ray",
  ...
}

Where the block lives. A corpus-wide default block (the N17XX permutations) goes in one typed authority file under data/atc/, loaded through the same schema machinery as other policy vocabulary. A scenario only writes its own block when its callsign differs — the Canadian file, the formation files, the BATC scenarios that already carry per-scenario tails like N172SB. Requiring ALL keys whenever a block is present is enforced by the schema, so a scenario can never declare half a callsign.

What 'require all permutations' buys you. Every spoken form that appears in radio text is human-authored and review-gated, exactly like every other piece of gold. When a reviewer certifies a scenario, the callsign forms are part of what they certify — grounded against AIM 4-2-4 (initial contact uses the full callsign; ATC may initiate abbreviation; type or model name may replace 'November'). No code rule ever has to encode that AIM section.

Where the old derivation idea still earns its keep

Demoted from authority to lint: expand_callsign() stays as a consistency CHECKER that warns when a declared spoken form doesn't match the registration's phonetic expansion (catching typos like 'November One Seven X-ray Yankee' under N17XX). A warning blocks nothing by itself — a human resolves it. Derivation checks; config decides.

DECISION 2

The 78 Flagged Rows — What Each Class Actually Is

The review fleet read 4,528 callsign mentions in radio text. 4,450 were the ordinary ownship callsign (they wait on Decision 1). These 78 were flagged as NOT ordinary. Four kinds, each explained with a real row.

Deliberately weird on purpose — 36 rows, leave alone

Two scenarios USE the callsign as their subject matter. phonetic_spelling_request (25 rows) stages a controller confusing 17XX with 17XY, forcing the pilot to spell the tail out — if a sweep replaced '17XX' with a placeholder, the scripted confusion pair and the spelling exercise stop matching and the scenario is destroyed. oshkosh_airventure_arrival (11 rows) models AirVenture arrivals, where controllers deliberately address aircraft by color and type ('red and white high-wing, rock your wings') INSTEAD of callsign — the scenario tests callsign ABSENCE. Recommendation: mark these rows leave-verbatim in the inventory so no future sweep ever touches them.

Right callsign, shouty spelling — 23 rows, template with casing kept

Example: a go-around phase written entirely in caps for urgency — 'NOVEMBER ONE SEVEN X-RAY X-RAY, GO AROUND'. That IS the standard ownship callsign; the sweep missed it only because it matched the exact mixed-case string. Recommendation: these fold into the Decision-1 sweep with a case-insensitive match that re-emits in the row's own casing (caps stay caps). Purely mechanical once Decision 1 lands.

Partial matches on foreign callsigns — 17 rows, per-scenario config

Example: the Yellowknife training flight. Ownship there is Canadian C-GXXX, abbreviated on the radio as 'Golf X-ray X-ray X-ray'. The residual scanner saw 'X-ray X-ray' inside that phrase and flagged it — but it's the TAIL of the Canadian abbreviation, not an N17XX form. A blind N17XX-based replacement would produce 'Golf {{placeholder}} X-ray' — garbage. Recommendation: these 17 rows substitute from their own scenario's callsign_config block (which is exactly what Decision 1 makes possible), never from the corpus default. Any row whose scenario lacks the needed key fails closed and gets hand-reviewed.

Somebody else's airplane — 2 rows, no action

Example: 'traffic Warrior crossing' — the tower telling us another aircraft (a Piper Warrior) is crossing the runway. 'Warrior' is that other plane, not us. The sweep correctly left both rows alone; they're in the flagged list only because the scanner can't tell whose airplane a word refers to. Nothing to do.

DECISION 3

Formation Flight: Which Airplane Is 'Us'?

Two scenario files, one question the templating machinery cannot answer by itself.

The situation. Two scenarios stage a two-ship formation flight: N17XX flies lead, N17XY flies wing. Every other scenario in the corpus has exactly one ownship — the aircraft whose radio we are, whose readbacks get scored, whose instructions reach the flight manager. The templating sweep needs to know which tail becomes {{CALLSIGN}}; it cannot template a file with two candidate ownships.

Why it matters downstream. Whoever is ownship: their readbacks are scored gold, ATC calls addressed to them must produce flight-manager proposals, and the OTHER aircraft's transmissions become ambient party-line audio (heard, never answered). Pick wrong and the scenario scores the wrong airplane's obligations.

How formation radio actually works. In a formation, the flight talks as ONE station — lead transmits for the flight, ATC addresses the flight through lead, wing stays off the radio. So the aviation answer and the modeling answer point the same way.

Recommendation: ownship = N17XX (lead). It matches the corpus default tail, matches how formation communication really works, and makes the wing's rows ordinary ambient audio — a shape the corpus already models everywhere else. N17XY then stays a literal string in the text, exactly like any other aircraft's callsign.

The alternative — modeling 'the flight' as a collective station — would need a new station concept the system doesn't have, for two files. Not worth inventing.

DECISION 4

The Stale Tripwire Test

A test has been red for five weeks for a boring reason. Fixing it needs your sign-off because of what the test protects.

What the test is. test_grounded_sources.py keeps a hardcoded list of every scenario allowed to claim 'grounded' status. It's a tripwire: if anyone — human or agent — flips a scenario's grounding_status field without going through review, the list doesn't match and the test screams. The list being hardcoded is the point.

Why it's red. On July 7 (and in waves since), twelve scenarios were legitimately promoted to grounded — each with review receipts and your approval at the time. Nobody updated the tripwire list. So for five weeks the test has been failing on promotions that were completely proper.

What the fix is. Add the twelve IDs to the list. That's the whole change.

Why I'm asking instead of just doing it. Updating a tripwire's expected list is exactly the move a sloppy agent makes to silence a failing test — the repo's gate law says test-oracle changes get explicit approval and a receipt, precisely so 'update the list' can't become a habit that kills the tripwire's value. Each of the twelve has an approval trail, so this roll is legitimate — but it's yours to authorize.

The risk of leaving it red. A permanently red tripwire protects nothing: the NEXT unauthorized grounding flip would hide inside the known failure. Rolling the list re-arms it.
