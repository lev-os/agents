How to name this

Which technique, in what order

Naming something this tangled fails if you start by picking words. Top domain modelers (Evans' ubiquitous language, concept mapping, formal concept analysis) work in this order:

  1. Inventory: every word in play, with where it came from. That is the table at the bottom of this page.
  2. Whiteboard: how the words relate, as pictures, not definitions. Those are the diagrams below.
  3. Word × property grid: two words with identical rows are synonyms, so keep one. One word that needs two rows is overloaded, so split it. The grid below does this for the place words, and it answers most of the island question without anyone choosing a word.
  4. Pick words only for what is still contested, about 6 words. This is where /pov fits. It forces several framings: an npm user reading config, an agent grepping, you saying it out loud, a newcomer. Then it reduces to one pick. /pov is the right tool for step 4 and the wrong one for step 1.
  5. Lock the winners into dna/vernacular.yaml with a retired list and a guard test, so the eleventh version can't come back.

Naming tests for each winner: it greps uniquely, it's speakable, it doesn't collide with a taken word (provider is taken), places get nouns, mechanisms get verbs.

The untangling

What I think each word is (dna, ir, lev ir, arch ir, ontology, graph, structure, meta structure, process)

You asked me to say what I think it is. Here it is, in one picture and one table.

Three layers, six facets. Every one of your words is either a layer, a facet, or a synonym for one of them.

  • Ontology (the meta-structure): the kinds, their relations and their lifecycle stages. What CAN exist. Small. Base kinds in core; plugins add namespaced kinds.
  • Instances (the material graph): the actual tasks, modules, checks, flows, typed by the ontology. Authored in fractal roots; mirrored into core/context-graph as a read model.
  • Projections: generated from instances, never edited: the command registry, rulebook prose, entities.yaml, gate views, SKILL.md, this page.

Lev IR = ontology + instances, in the stages candidate → admitted → resolved. Machine-readability is not the test: task.yaml is IR whether or not code reads every field, because it is an instance of a declared kind. But a field the ontology does not declare is cruft, which is what makes hygiene a diff.

The facets are the columns: structure, work, policy, execution, knowledge, vocabulary. The Lev IR plan already calls them "typed facets connected by references" (D1).

Where the current 'DNA' content goes, by facet (your question: if it all found a proper home, where?):

  • checks with a runnable test → policy facet, next to the owner; core/eval decides verdicts. Today only dna/core checks run.
  • rules with no test → the owner's spec as guidance (docs), until a test exists.
  • import allowlist, write authority → structure facet, one system-level instance, enforced by core/validator.
  • module identity, owns / does-not-own → the module's config.yaml (owns:, entity_definitions:) and README.
  • behaviors meant to run → flows. Failure modes → the flow's failure branches, or docs.
  • entity kinds and schemas → entity_definitions in the owner's config; schemas beside it.
  • process specs: escalation stages, idle loop, KPIs, test strategy → execution facet under plugins/sdlc: flows if runnable, docs if not. The core loop is the base flow they extend.
  • vocabulary, primitives → the vocabulary facet, one file, each term with an owner.
  • doctrine, rulings, history → docs and decision records.
  • task dna.yaml → task.yaml, the work facet's task spec.
  • other projects' YAML → their repos, using the published facet schemas; freeform notes stay theirs.

What the exercise found missing (gaps, not opinions): a stage field on most instances; a trigger/hook kind and vocabulary; an exec-spec kind (exec.yaml is authored, runtime_binding is derived; they are different things); a general current-vs-target field beyond gates; a vernacular resolver; the hygiene diff; and two names (FlowMind's compiled graph, the base ontology's owner package).

DNA, taken apart

What 'DNA' actually is: 18 families, and what a program reads

Four agents read every file section by section: 44 module rule files, 18 plugin files, plugin-local DNA, 17 .dna.yaml files outside dna/, the 27 architecture files, 14 standards, 7 authoring guides, 7 gate homes, the root doctrine files, and all 291 task packets. The reports are in .lev/pm/reports/2026-09-29-dna-census/.

The headline: the only part of 'DNA' any program runs is a rule's id + check (a shell command) + enforcement label. Two readers run these: tooling/scripts/run-dna-ratchet.js and core/validator, and only for dna/core. Everything else is notes, or it's read by one narrow script. The core agentic loop (plan, execute, verify) reads no root DNA. Its only DNA input is a task's acceptance list, which becomes the exit requirements (task-exit-requirements.ts:133).

/pov result on DNA (four turns plus a room test, 2026-09-29, pending JP)

Proposed rule: Something is IR only if a deterministic program reads it and a test proves that program rejects a bad one. Everything else is documentation, and is called that. An LLM reading text is prompt context, not IR (the translator boundary, applied to canon).

What survives as IR (each already has a program reader):

  • checks: id, one-sentence rule, check command, a should-fail case, gate or advisory.
  • boundaries: which package may import which, and who may write what.
  • entity kinds: in the owner's config.yaml.
  • registries: uri schemes, namespaces.
  • task spec: intent, acceptance, verifier.

Behaviors meant to run become flows. The rest moves to docs: README or spec, design docs, SDLC docs or flows, decision records, agent config, other repos.

Your questions, answered from the census (evidence, with inferences marked):

  • What is architecture? Three different things share the word. (1) System structure: which package may import which, layers, who may write what. It spans modules, and it's the only architecture any code consumes. (2) Feature seams: contracts for one cross-module feature, like tmux; nothing runs them. (3) Process: cascade stages, task-bundle lifecycle, success criteria. That's how we work, which is SDLC, not what the system is. Also, 366 of 412 module checks only grep their own folder, so most 'architecture' rules are per-module copies: no_plugin_imports appears 13 times.
  • Is it domain-based? Not today. Root dna/ is organized by topic (vocabulary, graph, testing), not by owner, even though dna/fractal.yaml:127 says the module name is the address.
  • Does it scale? No (inference from evidence). There's no schema: 447 keys, 167 more in task packets. Rules are copy-pasted across modules. The copies drift: id-aliases 10 vs 8; sdlc's flow list says 18 while config declares 36 and there are 42 on disk.
  • Core agentic loop? It runs without DNA. The verify command comes from execution.yaml, and the only DNA it reads is task acceptance. So 'DNA outranks code' (dna/index.yaml) is a claim the loop doesn't enforce.
  • Rebuild-from-nothing versus vast multi-party scale (inference): rebuilding from nothing needs a small, self-checking core, where every rule carries its check and a should-fail case, because prose can't bootstrap anything. Multi-party scale needs typed, owner-namespaced, versioned kinds with collision rules. Today's DNA has neither.

Your read is right: it grew into a god object. Evidence (Python scan of every tracked dna/*/.yaml, .dna.yaml and plugins//dna/*.yaml, 188 files, 0 unparseable):

  • No schema in practice. 447 different top-level keys; 344 of them appear in exactly one file. A schema does exist (plugins/dna/schemas/dna.feature.schema.yaml, 31 keys, additionalProperties: false). 69 of 79 *.dna.yaml files fit it, but only 71 of the 188 files overall do. 76 files have none of the three sections (constraints, behaviors, failure modes) that canon says make something DNA (dna/authoring/boundaries.yaml:15, 'DNA is a concept, not a file format').
  • About half the rules can't be enforced. 915 rule items: 440 have a runnable check, 340 have no check at all, 70 have an echo/manual check, and 65 have a check written in prose. 73 rules are labelled enforcement: gate with no runnable check. 191 more say catalogue and 122 say aspirational.
  • It's mostly prose. 71% of all text characters sit in description, rationale or notes fields or in strings over 160 characters. That's a spec written as YAML.

(The rule classes come from a heuristic on the check text: vitest|pnpm|rg|grep|test counts as runnable; echo|manual does not. That's an inference, not proof the command passes.)

The decision underneath all of this: what does the word 'DNA' mean? (A replacement for my own earlier shorthand. 'That goes in the DNA' was meaningless. From here on the page says which of the 13 things above, and in which file.)

  • (a) DNA means only the contract. A contract is rules with checks, guidance, behaviors and failure modes, using the schema that already exists, and it compiles to FlowMind. Everything else gets called what it is: vocabulary, entity kind, gate view, doctrine, spec. The dna/ folder can still host those, but they stop being 'DNA'. Example: vernacular.yaml is 'the vocabulary', not 'DNA'.
  • (b) DNA means the typed declarative layer. Every file starts with kind: from a short closed list (contract, vocabulary, entity, seam, standard, intent, doctrine, notes), and each kind has a published schema. This is how Kubernetes made freeform YAML into a standard: apiVersion + kind, one schema per kind. Your other projects would write kind: contract or kind: notes and get validation from lev dna validate. notes is the honest home for spec-as-YAML: allowed, machine-readable, never authoritative. Example: testing.yaml becomes kind: notes until someone gives it a schema.
  • (c) Retire the word. Say 'contract' and name every other kind. Example: dna/ is renamed canon/.

Recommendation: (b), with (a)'s discipline inside the contract kind. It's the only option that gives your outside projects a standard that still allows freeform notes. It keeps the word you and the LLMs already use. And it forces every file to say what it is, which is exactly what's missing today. Confidence: medium. It's a naming and standard decision, so it's yours.

Three smaller rules, the same under any option:

  1. A rule with no runnable check is guidance, never a gate. That relabels 73 rules currently marked enforcement: gate, which needs your OK because gates only ratchet forward.
  2. Prose over one line moves to a spec and gets linked.
  3. One file, one owner, one kind.
