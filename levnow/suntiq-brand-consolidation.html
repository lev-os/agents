The one that changes the plan

design-system/src/assets/brand/ is not a hand-maintained copy — it's generated output. export-brand-assets.mjs calls rmSync on it and repopulates it every run, and its files are byte-identical to the brand/ masters. It exists for exactly one reason: to give Wordmark.tsx something a bundler can resolve. Remove that need and the directory, the 2.4 MB, and a whole projection disappear together.

WHAT'S ACTUALLY BROKEN

Three real conflicts, not just duplication

Copies are annoying. These change what renders.

Two brand accents ship simultaneously

The website declares accent: "#27C6E6". The token treaty declares --ice: #00E5FF. Both are live. This is the same cyan-vs-cyan conflict the design-language work flagged back in July and never resolved — it just got hardcoded into a second place while nobody was looking.

Needs your call. Everything else on this page is mechanical.

Two font registries in one package

fontRegistry.ts holds 36 typed pairings and is the public API — FONT_PAIRINGS, getPairing, loadPairing, resolvePairingFonts. themeRecipe.ts holds 26 more, plus its own Google Fonts and Fontshare URL builders and its own fallback stacks.

The theme panel and the exported API can disagree about what fonts the brand has.

2.4 MB of logos compiled into JavaScript

Wordmark.tsx resolves six PNGs through new URL(..., import.meta.url). Under Vite library mode that inlines them as base64 rather than emitting files — 2.4 MB of PNG becomes ~3.3 MB of string.

That is the entire explanation for a 3.4 MB dist/index.js. Every consumer parses it on every load.

THE WORK

Four moves, in this order

Only the first needs a decision from you.

1 · Settle the accent, then make it unrepeatable

Pick #00E5FF or #27C6E6. Delete the loser everywhere. Then website/src/config/brand.ts stops holding a hex at all — it reads the CSS custom property, the same way every other surface does.

This is first because it's the only step that can't be done mechanically, and because the guard in step 4 can't be written until there's one right answer to guard.

2 · Cut the bundled logos — Wordmark resolves, doesn't import

Wordmark takes its artwork from a resolved path rather than a bundler import. Consumers already serve brand-kit/ statically: Storybook maps it to /brand-kit, the website has public/, fleet has public/.

When the new URL(import.meta.url) calls go, src/assets/brand/ has no remaining reason to exist — so the generator stops writing it, and dist/index.js drops from 3.4 MB to roughly 40 KB.

Watch for: Wordmark has a text appearance path that needs no artwork at all, and the website renders its own lockup through next/image. Neither should regress — both need a Storybook story before the change lands.

3 · One font registry, one loader

fontRegistry.ts wins — it's typed, tested by the exported API, and already public. themeRecipe.ts imports FONT_PAIRINGS from it and deletes its own 26 entries, its gfUrl/fsUrl builders, and its duplicate fallback constants.

The theme panel keeps working; it just stops having its own opinion about what fonts the brand owns.

4 · Make Storybook the brand console — and guard it

Foundations/Brand/Assets already renders the logo, social, and web-app matrices straight out of brand-kit/. Three things are missing:

A token page that reads the live CSS custom properties rather than restating them, so it cannot drift from the code.

An authority page rendering brand/manifest.yaml — approval status, version, and the sha256 of each master — so approval state is something you look at, not something you trust.

A staleness check, which is the part that makes the rest hold.

THE GUARD

Same trick that worked on vendor

You liked that the build fails closed. Brand has two equivalents.

design-system/scripts/check-brand-drift.mjs
/* Two failures, both fatal, both cheap:
 *
 * 1. brand-kit/ is stale — a master in brand/ no longer matches the
 *    sha256 that manifest.yaml approved, or a derivative is missing.
 *    Someone dropped a new logo in and didn't re-run the generator.
 *
 * 2. a brand value is hardcoded outside the token layer — a hex, a
 *    font family, a logo path written by hand in an app instead of
 *    read from tokens or brand-kit.
 */

const approved = readManifest("brand/manifest.yaml");

for (const [file, sha] of Object.entries(approved.release.sha256)) {
  if (sha256(file) !== sha) fail(`${file} drifted from its approved hash`);
}

for (const asset of readKitManifest().assets.flatMap((a) => a.files)) {
  if (!exists(asset.path)) fail(`brand-kit missing ${asset.path} — re-run brand:export`);
}

// hex literals are the ones that actually bite; tokens are the only
// place a brand colour may be spelled out.
for (const hit of grepOutsideTokens(/#(?:00E5FF|27C6E6|0B1320)/i)) {
  fail(`${hit.file}:${hit.line} hardcodes a brand colour — read the token`);
}
Why this is the whole point

The vendor guard worked because it made the wrong thing impossible rather than merely discouraged.

Brand drift has the same shape. Nobody consolidates a brand once — it re-scatters the next time someone needs a logo in a hurry. A check wired into prebuild means the next hardcoded hex fails a build instead of quietly becoming the ninth authority.

It hooks in exactly where the vendor check already does.
