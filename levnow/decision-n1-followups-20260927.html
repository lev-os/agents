MY ANSWER

Claude, this session (informed, so weigh it less)

Yes, but not in this shape. Tonight's numbers, all re-checked by me:

  • 60 of 98 sampled commits are governance, 9 are user-facing. 12 of 50 gates are enforced and none run automatically.
  • lev status exits 2, lev task list fails, lev search goes to an unimplemented catalog.
  • Jarvis imports lev in 117 files; the next app, 17. 20,756 tracked files sit in Python virtualenvs.

What is worth keeping are the ideas that nothing else has together: only one module decides truth, every effect leaves a receipt, gates only ratchet forward, and one declaration projects to CLI, MCP and HTTP.

What is not worth it is the breadth: 44 core packages, 65 plugins and 42 crates for one operator and one real consumer. Breadth creates split-brain; split-brain creates rulings, records and vocabulary; those become more for every agent to read. This session is the example: hours of work, zero user-facing change.

Your alternative is closer than it sounds. Poly already is the CLI/MCP/HTTP builder, built from module declarations. "Gates + builders" = poly + the 12 enforced gates + the modules Jarvis actually reaches. That is a cut, not a rewrite.

What I would do: freeze new modules, records and rulings for 30 days; delete the virtualenvs; make each declared gate run or delete it; archive what Jarvis does not reach; rerun the 14/15 DNA experiment blind against a one-page contract; track user-facing commit share weekly.
