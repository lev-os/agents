One Rule, Three Referees

The repo enforces the same rules in three different places. Here is what that means, what four AI advisors said about fixing it, and the single decision you're being asked to make.

Leviathan · July 2026

No jargon past this point without a definition. Read the first two sections and you'll understand everything the terminal conversation was about.

THE PROBLEM

The same rule is written down — and checked — in three places

And the three copies don't stay in sync.

Leviathan has house rules like "no code may scan folders directly — it must go through the one approved door" or "every module must declare its name in the registry."

Right now, a rule like that can be enforced by three separate pieces of machinery at once: a schema that checks config files, a test suite that scans the source code, and a rulebook entry that carries its own little hidden check-command inside it. Three referees, one rule.

Why is that bad? Because when the code changes, someone updates one referee and forgets the other two. The forgotten ones keep waving green flags for a rule they're no longer actually checking. You believe the rule is enforced. It isn't. That silent wrong-green is the failure we're designing against.

Today: three referees per rule — and one of them may be checking nothing.

The failure mode has a name: false-green

A check that passes not because the rule is followed, but because the check quietly stopped working. It's worse than a failing check — a failing check gets fixed; a false-green gets trusted.

The five words the terminal kept using

Every term from the conversation, in normal English.

A REAL EXAMPLE

One rule, three places it lives today

The 'no raw folder scanning' rule — the one that caught two real violations this month.

📖

In the rulebook

A DNA file states the rule — and embeds a shell command (a text-search) that a runner executes to check it. If the code moves, the text-search finds nothing and reports green forever. Nobody is alerted.

🧪

In the test suite

A dedicated lint (the 'scanner census') scans all source for raw folder-reads and fails loudly with instructions when it finds one. This copy works — it caught two violations from parallel sessions within days. This is what a good referee looks like.

📋

In the validators

Separate structural validators re-check overlapping facts about module shape — and one of them accepts module types the official schema rejects. The referees don't even agree on the rules.

THE PROPOSAL

What 'declaration-only' changes

Same rulebook, but it points instead of pretending to enforce.

Before
BEFORE — rule with a hidden program inside
rule: "No raw folder scanning outside core/config"
check: |
  grep -rn "readdirSync" core plugins \
    && exit 1 || exit 0
# ^ a mini-program buried in the rulebook.
#   When code moves, it silently stops
#   finding anything — and stays green.
After
AFTER — rule that points at its referee
rule: "No raw folder scanning outside core/config"
enforced_by:
  instrument: tests/lint/scanner-census.test.ts
  kind: lint
# ^ no hidden program. One real test enforces
#   this rule. A new meta-lint verifies this
#   pointer names a test that exists AND runs.

Three Claude models (haiku, sonnet, opus) got the identical neutral question independently. VERIFIED FINDINGS

Sol's four landmines

Why the migration must be careful, not big-bang.

1 · Some rulebook entries are shipped product

The DNA compiler turns rule entries into live runtime gates that ship to users. Stripping their executable parts wouldn't just clean the repo — it would change how the product behaves. So: remove hidden shell commands, keep typed runtime policy.

2 · A pointer put in the old field gets EXECUTED

Both existing rule-runners treat the check field as a shell command and run it. Write a file path there and the system tries to execute the path as a command. A new, separate field must exist before any rule migrates.

3 · The surface is ~460 hidden commands, not a handful

Counted directly: 461 embedded check/eval strings across the rulebook, plus 24 module files carrying a second duplicate copy of their checks in a script block. Migrating only the obvious field leaves a live twin behind.

4 · 'The file exists' is not 'the test runs'

One current validator already demonstrates the trap: it parses the rulebook, counts entries, and always reports green — it never runs anything. So the meta-lint must verify each pointer's referee actually executes in an enabled pipeline, not merely that a file with that name exists.

THE ROUTE

The migration order both advisors converge on

Each step makes the next one safe.

Step 1

Add the new pointer field

Teach the rulebook format and both rule-runners about a typed 'enforced_by' field — so a pointer is never mistaken for a command (landmine 2).

Step 2

Ship the meta-lint

The pointer-checker: every rule's referee must exist AND be reachable in a pipeline that actually runs (landmine 4). This ships before any rule migrates — the caveat all three tribunal models insisted on.

Step 3

Migrate rule by rule, with proof

For each rule: confirm the real referee exists, deliberately break the rule once to watch the referee catch it, flip the rule to a pointer, delete the hidden command AND its duplicate twin (landmine 3). Shipped-runtime entries keep their typed policy (landmine 1).

Step 4

Delete the shell runner

Only when a census counts zero hidden commands left in the rulebook does the machinery that executed them get removed. No compatibility layer stays behind.
